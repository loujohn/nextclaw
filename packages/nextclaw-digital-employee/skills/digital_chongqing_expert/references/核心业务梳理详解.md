# 核心业务梳理详解

本文档基于《渝数建办〔2024〕29号-核心业务梳理操作指南2.0版本》及数字重庆核心业务梳理实施经验整理，旨在指导各部门、区县及企事业单位开展核心业务梳理工作。

## 一、 核心概念定义

### 1. 核心业务 (Core Business)
核心业务是基于职权责任体系、阶段性重大任务和关键绩效指标（KPI）所形成的基础、重点、应急等事项。
- **构成要素**：包括目标、指标、工作、政策及评价体系。
- **来源维**：
    1.  **上级部署的重大任务**：党的二十大、二十届三中全会部署，习近平总书记视察重庆重要讲话重要指示精神，市委市政府重点工作等。
    2.  **职权责任体系**：部门“三定”方案明确的主责主业。
    3.  **问题导向**：基层企业群众反映的突出问题，跨部门、跨层级、跨领域的堵点卡点。
    4.  **KPI与急用先行**：最迫切的业务需求及关键绩效指标。

### 2. 业务事项 (Business Matter)
能具体表述部门履职内容的**最小单元**。
- **命名规范**：`主语 + 谓语 + 宾语`（主语为责任部门时可省略）。例如：“发布征求水旱灾害预防年度投资计划意见通知”。
- **“最小”标准**：
    1.  **不跨部门和层级**：由单一部门内部完成。
    2.  **不可分割性**：需完整执行，或者为满足协同模型需求而不必拆解。
    3.  **相对性**：不同复杂度的业务（如“现场核实”与“行政处罚”）只要符合上述标准，均视为最小颗粒度，无需比较大小。

### 3. 数据集与数据项 (Data Set & Data Item)
描述业务事项办理流程中的数据内容。
- **输入数据集**：办理业务所需的数据（需求数据）。
- **输出数据集**：办理业务产生的数据（结果数据）。
- **数据项**：数据集中的具体字段（如：姓名、水位、时间）。

## 二、 V模型梳理方法论

核心业务梳理遵循“V”模型方法，包含**自上而下的拆解**和**自下而上的集成**两个过程。

### 1. V字下行：层层细化（拆解分析）
**目标**：将宏观任务拆解为可操作的最小单元，实现业务的“数字化”与“量化”。
- **路径**：`核心业务 -> 一级业务 -> 二级业务 -> ... -> 业务事项 -> 数据项`
- **操作**：
    - 对照重大任务和KPI，确定核心业务。
    - 逐级拆解直至独立的“业务事项”。
    - 找出每个业务事项对应的指标和数据项。

### 2. V字上行：综合集成（重构优化）
**目标**：通过流程再造，将分散的业务事项重构为高效协同的“一件事”，实现“体系重塑”。
- **路径**：`优化后的业务事项 -> “一件事”场景（一级场景/二级场景） -> 重构后的核心业务`
- **操作**：
    - **归并**：按同类归并原则，合并重复或相似事项。
    - **协同**：按关联协同原则，串联跨部门事项。
    - **重组**：将数据项重组为新的业务指标，构建支撑KPI的“四梁八柱”。
    - **再造**：运用数字化手段消除冗余、堵点，形成新的业务流程。

## 三、 梳理实施步骤

### 第一步：确定核心业务
从三个维度确定本单位核心业务：
1.  **对标对表**：将工作主线与上级重大部署、KPI对接。
2.  **问题导向**：聚焦条块分割、各自为政的堵点，以及群众高频需求。
3.  **急用先行**：聚焦防汛、防火、风险防范等最紧迫任务。

### 第二步：全量梳理与拆解 (V模型下行)
1.  **构建业务树**：按照业务逻辑，将核心业务拆解为多级业务架构。
2.  **定义事项**：确保底层叶子节点为符合“最小颗粒度”标准的业务事项。
3.  **数据挂接**：为每个业务事项梳理“输入”和“输出”数据项，明确数源部门和数据格式。

### 第三步：问题分析与流程再造 (V模型底部)
在梳理过程中同步开展分析：
- **流程解析**：是否存在冗余环节？
- **效能分析**：是否存在堵点卡点？
- **法律依据**：是否有明确法规支持？
- **改革谋划**：针对问题，提出体制机制改革或数字化优化举措。

### 第四步：集成与架构重构 (V模型上行)
####  **“一件事”思维**：将相关联的单项业务整合为“一件事”。
#### **场景谋划**：核心业务呈现的两种范式——“链式”与“团式”
在构建一级场景（一级业务）时，根据业务性质不同，主要有两种构建逻辑：
##### 1. 链式（流程闭环型）
- **适用场景**：适用于应急指挥、全生命周期管理等具有明显时间先后顺序的业务。
- **构建逻辑**：按照事件发展的闭环过程，将每一个关键环节作为一个一级场景，首尾相连构成闭环。
- **典型案例（突发事件直报快响）**：
    - 环节一：**事件感知**（事前/触发）
        
    - 环节二：**调度处置**（事中/执行）
        
    - 环节三：**事件复盘**（事后/评价）
        
##### 2. 团式（领域聚合型）
- **适用场景**：适用于政务服务、综合管理等包含多个平行职能领域的业务。
- **构建逻辑**：分领域构建一级场景，列出该领域内的重点任务。各领域相互支撑，共同构成完整的服务或治理体系。
- **典型案例（警快办）**：
    - 领域一：**车驾**（车辆与驾驶员管理）
    - 领域二：**户政**（户籍管理）
    - 领域三：**出入境**（证件与通行）
    - 领域四：**治安**（公共安全）
    - 领域五：**电子证照**（基础支撑）

> **⚠️ 架构图绘制常见问题诊断（避坑指南）**：
> 1. **闭环缺失**：一级业务不闭环，**缺得最多的是“事件复盘”环节**（只管做，不管评）。
> 2. **逻辑混乱**：二级业务分类无逻辑，像是随意堆砌。
> 3. **颗粒度过粗**：数据共享和业务协同的点不精准，描述太宏观（如只写“共享数据”，未指明具体是“身份证号”还是“人脸影像”）。
> 4. **协同虚化**：业务协同关系显得比较“横”（泛泛而谈），没有落实到具体事项的触发与流转。
#### **驾驶舱构建**：将核心业务转化为驾驶舱一级场景，细分业务转化为下钻场景，并关联KPI。
### 第五步：数字化编目
将梳理成果（架构体系、业务清单）录入“数字化应用管理系统”的“核心业务模块”。
- 标记已数字化事项。
- 动态更新编目。

## 四、 核心业务数字化率评价

核心业务数字化率是衡量单位基本能力建设的重要指标。

**计算公式（参考）：**
> **核心业务数字化率** = (本单位业务事项编目数 / 本行业平均编目数 × 10%) + (已数字化事项数 / 本单位业务事项编目数 × 90%)

*注：(编目数/平均数) 权重上限为1。*

**指标说明**：
- **已数字化事项**：指与IRS上“建设中”、“运行中”应用关联的事项，或与三级治理中心智能预案关联的事项。
- **目标**：部门(>90%)、区县(>80%)、镇街(>95%)、国企/高校/医院/金融机构(>90%-95%)。

## 五、 常见问题与避坑指南

| 问题现象 | 原因分析 | 纠正措施 |
| :--- | :--- | :--- |
| **业务颗粒度不均** | 未遵循“最小单元”标准，有的拆得太细（动作级），有的太粗（任务级）。 | 严格判据：是否跨部门？是否需完整执行？ |
| **一级业务不闭环** | 往往缺失“评价复盘”或“监督监管”环节。 | 检查业务链条是否包含“感知-决策-处置-评价”全闭环。 |
| **数据需求空泛** | 仅填写“共享XX数据”，未明确到具体字段。 | 必须细化到“数据项”（如：身份证号、企业信用代码）。 |
| **协同关系横向化** | 协同点不精准，甚至随意勾选无关部门。 | 基于实际业务流转逻辑确定上下游协同部门。 |
| **为梳理而梳理** | 仅做存量业务搬家，未发现问题，未做流程优化。 | 核心目的是**改革**和**解决问题**，必须输出问题清单和改革清单。 |

## 六、 成果产出
1.  **核心业务架构图**：展示核心业务到具体事项的层级关系。
2.  **业务事项目录表**：包含事项名称、依据、基础信息等。
3.  **“三张清单”**：
    - **需求清单**：业务需求与数字化需求。
    - **改革清单**：制度重塑与流程再造举措。
    - **应用清单**：需开发的数字化应用功能模块。
## 附录一：核心业务架构图参考样例

以下样例基于真实梳理经验（政府部门与国有企业）提炼，供绘制架构图时参考“V模型”的层级逻辑。

### 样例一：政府部门视角（以水利局为例）

**逻辑主线**：围绕“防灾减灾”职能，从宏观防御目标拆解至具体调度动作。

|层级|示例名称|梳理逻辑与说明|
|---|---|---|
|**核心业务**|**水旱灾害防御**|对应上级“守住水安全底线”的重大任务与KPI。|
|**一级业务**|山洪防御 / 干旱防御|按灾害类型或防御阶段进行宏观分类。|
|**二级业务**|**河道行洪** / 水库行洪|具体的业务场景或管理对象集合。|
|**业务事项**|汛期调度|**最小颗粒度动作**：不仅是“调度”，还包含输入（水位数据）与输出（调度指令）。|
|**业务事项**|汛前检查|具体的检查动作，包含输出检查报告。|
|**业务事项**|熵情监测|具体的监测动作，产生实时监测数据。|

### 样例二：国有企业视角（以项目管理为例）

**逻辑主线**：围绕“经营效益”目标，从全生命周期拆解至具体执行环节。

|层级|示例名称|梳理逻辑与说明|
|---|---|---|
|**核心业务**|**项目全流程管理**|对应企业“降本增效、合规经营”的战略目标。|
|**一级业务**|承建项目管理|按项目性质分类（如自建、承建、投融资等）。|
|**二级业务**|**项目投标管理**|项目全生命周期的具体阶段。|
|**业务事项**|编制投标收益测算表|**最小颗粒度动作**：具体的财务测算动作。|
|**业务事项**|组织标前评审|具体的会议/评审动作，需输出评审意见。|
|**业务事项**|申请用印|具体的行政审批动作，是投标流程的关键节点。|
|**业务事项**|进行投标活动|具体的执行动作，输出投标结果。|

## 附录二：《业务事项目录表》填写指南与样例
本表用于将拆解出的“最小颗粒度”事项标准化，明确责任主体与数字化支撑情况。以下样例摘自市水利局“河长管河治河”核心业务梳理成果。

### 1. 表格结构与填写说明
|关键字段|填写说明|
|---|---|
|**业务事项名称**|必须具有**唯一性**，准确反映业务内容，通常采用“**动词+名词**”结构。|
|**业务事项描述**|简要描述该事项的具体操作内容、触发条件及工作目的。|
|**业务事项类型**|通常分为：行政许可、行政处罚、行政强制、**交办**、自办、公共服务等。|
|**现有系统名称**|如果该事项目前已有信息化系统支持，填写系统全称；若无则留空。|
|**规划应用名称**|该事项计划纳入的“三融五跨”重大应用名称（如：政务·智慧河长）。|
|**依据文件描述**|**必须具体**：列出法律、法规、部门规章或“三定”方案的具体名称。|

> **专家提示**：
> - **颗粒度自检**：如果一个事项需要跨部门流转，或者包含多个必须中断的步骤，请检查是否需要进一步拆解。
> - **数字化关联**：填写“现有系统”和“规划应用”字段是后续计算“核心业务数字化率”的关键依据。
> **专家提示**： 核心业务梳理是一个**动态迭代**的过程。随着工作的推进（如新的上级部署、新的突发情况），核心业务架构图和事项清单应及时更新，保持“账实相符”。
