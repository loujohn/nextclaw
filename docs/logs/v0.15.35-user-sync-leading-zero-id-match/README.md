# v0.15.35-user-sync-leading-zero-id-match

## 迭代完成说明

- 修复用户同步自动关联中的一类身份格式不一致问题：真实员工表中的钉钉 userid 可能保留前导 0，而人员同步接口返回的 dingTalkId 可能去掉这些前导 0，导致原先精确匹配失败。
- 在自动关联匹配层增加身份候选值生成逻辑：对纯数字身份同时保留原值与“去前导 0”后的值参与匹配。
- 该兼容逻辑同时覆盖真实员工侧索引构建和同步侧 DingTalkId 查询候选生成，确保像 `011208426431021667` 与 `11208426431021667` 这类场景可以正确命中。
- 仍保持“唯一命中才自动关联”的安全边界，若去前导 0 后出现多条候选，系统不会误绑。
- 补充回归测试，覆盖“真实员工 userid 有前导 0、同步 DingTalkId 无前导 0”时的自动关联成功场景。

## 测试/验证/验收方式

- 定向类型检查：pnpm exec vue-tsc --noEmit
- 定向静态检查：pnpm exec eslint server/services/user-sync-service.ts tests/user-sync-service.test.ts --ext .ts --rule 'max-lines: off' --max-warnings=0
- 编辑器问题检查：受影响文件未发现新增错误。
- 当前环境仍未执行数据库类 vitest 运行时校验，原因是达梦测试库连通性限制未解除。

## 发布/部署方式

- 本次仅涉及 nextclaw-digital-employee 包内的自动关联匹配逻辑与测试，无数据库 schema 变更。
- 可随下一次数字员工平台常规发布一并带出。
- 发布后建议在真实数据环境执行一次用户同步冒烟，重点检查此前因前导 0 未关联的人是否已自动关联成功。

## 用户/产品视角的验收步骤

1. 确认真实员工表中存在带前导 0 的钉钉 userid，例如 `011208426431021667`。
2. 执行“用户管理 → 同步人员”，确保外部接口返回的对应 dingTalkId 为去掉前导 0 的形式，例如 `11208426431021667`。
3. 同步完成后，返回用户列表，确认该同步用户已自动关联到真实员工，而不是进入“未关联人员”名单。
4. 若存在同一去前导 0 结果对应多条真实员工记录，系统应保持不自动关联，避免误绑。
