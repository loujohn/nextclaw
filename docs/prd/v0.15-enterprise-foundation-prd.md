## 一、产品背景与目标

### 1.1 背景

数字员工平台已具备基础运行能力（员工 CRUD、对话、技能绑定、定时任务、钉钉集成），但缺乏企业级落地的关键基础设施：

- **无用户认证**：所有接口裸奔，无法区分操作者身份
- **Skill 管理粗糙**：全局共享、单级分类、无法按员工定制
- **工作空间未隔离**：员工之间共享文件空间，对话无法附件交互
- **缺乏任务闭环**：真实员工与数字员工之间无正式的任务协作链路
- **消息来源不可追溯**：钉钉消息无法映射到具体真实员工

### 1.2 目标

将数字员工平台从"内部可用工具"升级为"可认证、可管理、可协同的企业级数字劳动力平台"。

### 1.3 成功指标

| 指标 | 目标 |
|------|------|
| 登录认证覆盖率 | 100% API 受保护 |
| Skill 管理粒度 | 每个员工独立 skill 副本 + 二级分类 |
| 文件交互完整度 | 对话可上传、AI 可生成、工作空间可浏览 |
| 任务闭环率 | 任务可创建→分配→完成→打分 |
| 消息溯源率 | 钉钉消息 100% 可关联到 human_employee |

## 三、特性需求详述

### 特性 1: 用户系统 + Keycloak 对接 [P0]

#### 3.1.1 用户故事

- **作为**系统管理员，**我希望**只有通过认证的用户才能访问平台，**以便**保障企业数据安全
- **作为**部门管理员，**我希望**只能管理自己部门的数字员工，**以便**职责边界清晰
- **作为**普通成员，**我希望**登录后直接看到自己有权限使用的数字员工，**以便**快速开始工作

#### 3.1.2 功能需求

**FR-1.1 登录认证**

| 项 | 说明 |
|----|------|
| 认证方式 | Keycloak OIDC + PKCE |
| 登录页 | 跳转 Keycloak 统一登录页，登录后回调到平台 |
| Token 管理 | Access Token + Refresh Token，前端自动续期 |
| 登出 | 同时清除本地 token 和 Keycloak session |

**FR-1.2 权限控制**

| 页面/功能 | admin | manager | user |
|-----------|-------|---------|------|
| Dashboard 看板 | 全局数据 | 本部门数据 | 仅个人相关 |
| 员工管理（CRUD） | 全部 | 本部门 | 只读（已授权的） |
| 员工对话 | 全部 | 本部门 | 已授权的员工 |
| Skill 管理 | 全部（含全局管理） | 本部门员工的 skill | 只读 |
| 集成配置 | 全部 | 只读 | 不可见 |
| 安全/密钥 | 全部 | 不可见 | 不可见 |
| 用户管理 | 全部 | 不可见 | 不可见 |
| 任务管理 | 全部 | 本部门 | 仅个人 |
| 组织架构 | 全部 | 本部门 | 不可见 |

**FR-1.3 首次登录自动注册**

- Keycloak 认证成功后，检查本地 `users` 表
- 若不存在，自动创建记录（默认 `user` 角色）
- admin 可在用户管理页调整角色

**FR-1.4 用户管理页面（仅 admin）**

- 用户列表：头像、姓名、邮箱、角色、关联部门、最后登录时间
- 角色调整：admin / manager / user 切换
- 部门关联：为 manager 分配管理部门

#### 3.1.3 非功能需求

- Token 过期时间：Access Token 5 分钟，Refresh Token 30 天
- JWKS 缓存：本地缓存 Keycloak 公钥，5 分钟刷新
- 降级策略：Keycloak 不可达时，使用缓存公钥验证已有 token（不允许新登录）

### 特性 2: Skill 改造 [P1]

#### 3.2.1 用户故事

- **作为**系统管理员，**我希望**为每个数字员工配置独立的 skill 副本，**以便**不同员工可以有定制化的技能配置
- **作为**部门管理员，**我希望**通过二级分类快速找到所需 skill，**以便**高效地为员工分配能力
- **作为**系统管理员，**我希望**可以一键将全局最新 skill 同步到指定员工，**以便**保持技能版本最新

#### 3.2.2 功能需求

**FR-2.1 员工独立 Skill 副本**

| 操作 | 行为 |
|------|------|
| 绑定 Skill | 从全局 `skills/` 复制完整目录到 `employees/{id}/skills/` |
| 解绑 Skill | 删除员工目录下的 skill 副本 + 删除 employee_skills 记录 |
| 从全局更新 | 用全局最新版本覆盖员工副本 |
| 批量更新 | 选中多个 skill 一键从全局同步 |
| 版本对比 | 显示员工副本与全局版本是否一致 |

**FR-2.2 二级分类**

- 一级分类保留现有 6 个，可由 admin 新增
- 二级分类为可自定义列表
- Skill 绑定时可指定分类（一级 + 二级）
- 前端按二级分类分组展示

预置二级分类：

| 一级 | 二级 |
|------|------|
| 项目管理类 | 甘特图制作、里程碑跟踪、资源调配、进度汇报 |
| 经营管理类 | 数据分析、报表生成、KPI 追踪、预算管理 |
| 产品研发类 | 需求分析、技术文档、架构设计、代码审查 |
| 市场营销类 | 内容创作、竞品分析、营销策划、社媒运营 |
| 解决方案类 | 方案编写、标书制作、咨询报告、客户分析 |
| 通用能力类 | 文档处理、演示制作、翻译校对、信息检索 |

**FR-2.3 Skill 分类管理页面（admin）**

- 一级分类 CRUD（名称、emoji、排序）
- 二级分类 CRUD（名称、父分类、排序）
- 分类下的 skill 列表预览

**FR-2.4 Skill 目录页改造**

- 左侧：分类树（一级 > 二级）
- 右侧：skill 卡片列表
- 每个 skill 卡片显示：名称、描述、分类、使用员工数、版本状态
- 筛选器：按分类、按使用状态、按来源

#### 3.2.3 运行时变更

- `EmployeeRunService` 准备运行时，从 `employees/{empId}/skills/` 加载 skill（非全局目录）
- 若员工目录下不存在某个 skill，回退到全局目录（兼容未迁移的旧数据）

### 特性 3: 工作空间文件管理 + 对话增强 [P1]

#### 3.3.1 用户故事

- **作为**普通成员，**我希望**在对话中上传文件给数字员工处理，**以便**提供必要的输入材料
- **作为**数字员工的操作者，**我希望**AI 生成的文件自动保存到工作空间，**以便**后续查找和下载
- **作为**部门管理员，**我希望**查看某个数字员工的工作空间文件，**以便**审查产出质量

#### 3.3.2 功能需求

**FR-3.1 员工工作空间隔离**

```
employees/{employeeId}/
  skills/        ← Skill 副本（特性 2）
  files/
    uploads/     ← 用户上传的文件
    outputs/     ← AI 生成的文件
```

- 创建员工时自动初始化目录结构
- 删除/归档员工时保留工作空间（不自动清除）

**FR-3.2 文件上传**

| 项 | 规格 |
|----|------|
| 上传方式 | 对话输入框拖拽 / 点击按钮选择 |
| 单文件大小 | ≤ 50 MB |
| 支持格式 | 不限（常见：doc/docx/xls/xlsx/ppt/pptx/pdf/txt/md/csv/jpg/png/zip） |
| 并发上传 | 支持多文件同时上传（最多 10 个） |
| 上传反馈 | 进度条 + 完成提示 |
| 存储位置 | `files/uploads/{原始文件名}` |
| 重名策略 | 自动追加序号：`report.pdf` → `report (1).pdf` |

**FR-3.3 对话中的文件交互**

- 用户发送消息时，可同时附带文件引用
- 消息体中显示附件缩略图/文件名
- AI 回复中引用的文件，显示为可点击链接
- `ChatMessageView` 扩展：

```typescript
type ChatMessageView = {
  role: "user" | "assistant" | "system" | "tool";
  content: string;
  timestamp?: string;
  toolCalls?: ChatToolCallView[];
  reasoning?: string;
  toolCallId?: string;
  toolName?: string;
  // 新增
  attachments?: ChatAttachment[];
};

type ChatAttachment = {
  filename: string;
  path: string;        // workspace 内相对路径
  sizeBytes: number;
  mimeType: string;
  isOutput?: boolean;  // true = AI 生成
};
```

**FR-3.4 AI 生成文件**

- AI 执行过程中通过 `write_file` 工具生成的文件 → 自动写入 `files/outputs/`
- 生成完成后，在对话中显示为附件卡片
- 支持直接下载

**FR-3.5 工作空间文件浏览器**

- 员工详情页 → "工作空间" Tab
- 双栏布局：
  - 左侧：文件树（uploads / outputs 两个根目录）
  - 右侧：文件预览区
- 支持操作：
  - 查看/预览（文本/Markdown/图片/PDF）
  - 下载
  - 删除（需确认）
  - 手动上传（非对话场景直接上传到 workspace）
- 文件列表信息：文件名、大小、修改时间、来源（上传/生成）

### 特性 4: 真实员工任务管理及打分 [P2]

#### 3.4.1 用户故事

- **作为**部门管理员，**我希望**为团队成员分配任务并跟踪进度，**以便**掌握团队工作状态

#### 3.4.2 功能需求

**FR-4.1 任务 CRUD**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 标题 | string | 是 | 任务名称 |

| 多次打分 | 允许修改评分（覆盖） |

**FR-4.4 任务关联**

**FR-4.5 任务看板页面**

- 每张任务卡片显示：标题、分配人头像、优先级标签、截止日期、评分（如有）

**FR-4.6 Dashboard 集成**

- Dashboard 新增任务统计卡片：

### 特性 5: 钉钉映射真实员工消息来源 [P2]

#### 3.5.1 用户故事

- **作为**系统管理员，**我希望**钉钉消息可以自动识别发送者对应的真实员工，**以便**追溯消息来源
- **作为**部门管理员，**我希望**数字员工可以向真实员工发送钉钉消息分配任务，**以便**实现任务分发闭环
- **作为**普通成员，**我希望**在钉钉群发送日报后被自动收集和汇总，**以便**减少重复工作

#### 3.5.2 功能需求

**FR-5.1 消息来源自动识别**

- 钉钉消息到达 Channel Runtime 后：
  1. 提取 sender 的 `userid`
  2. 查询 `human_employees` 表 (`external_id = userid`)
  3. 匹配成功 → 注入到消息上下文 `context.humanEmployee`
  4. 匹配失败 → 记录未知发送者日志，消息正常流转

**FR-5.2 钉钉主动发送**

- 数字员工可通过工具调用向真实员工发送钉钉消息
- 消息类型：文本、Markdown、Action Card
- 发送对象：指定 `human_employee_id` → 解析为钉钉 `userid` → 调用钉钉 API 发送

**FR-5.3 消息收集规则**

| 规则类型 | 触发条件 | 示例 |
|---------|---------|------|
| 关键词匹配 | 消息包含指定关键词 | 包含"日报"或"#daily" |
| 模板匹配 | 消息符合指定模板格式 | `[日报] 项目: ... 进度: ...` |
| 定时收集 | 在指定时间段内收到的消息 | 每天 18:00-20:00 收到的消息视为日报 |

规则可配置项：
- 规则名称、描述
- 匹配渠道（默认钉钉）
- 匹配条件（关键词列表 / 正则 / 时间窗口）
- 目标数字员工（由哪个数字员工处理收集到的内容）
- 启用/停用

**FR-5.4 日报周报收集流程**

```
员工在钉钉群发送日报
  ↓
Channel Runtime 接收 → 识别发送者
  ↓
消息收集规则匹配（关键词"日报"）
  ↓
提取结构化内容 → 存储到关联的 task/记录
  ↓
目标数字员工汇总分析
  ↓
生成汇总报告 → 发送给管理员
```

**FR-5.5 消息来源配置页面**

- 入口：集成管理 → 钉钉 → 消息来源配置
- 功能：
  - 映射关系总览（钉钉用户 → 真实员工，自动建立）
  - 收集规则列表（CRUD）
  - 规则测试（输入示例消息 → 显示匹配结果）

## 四、非功能需求

### 4.1 安全

| 项 | 要求 |
|----|------|
| 认证 | 所有 API 必须经过 JWT 认证 |
| 授权 | 基于角色的访问控制（RBAC） |
| Token 存储 | 前端仅存储在内存 + httpOnly cookie（不使用 localStorage） |
| 文件上传 | 校验文件大小、MIME 类型，禁止可执行文件 |
| SQL 注入 | Knex 参数化查询（已有保障） |

### 4.2 性能

| 项 | 要求 |
|----|------|
| 登录响应 | < 3 秒（含 Keycloak 跳转） |
| 文件上传 | 50MB 文件上传 < 10 秒（本地存储） |
| Skill 复制 | 单个 skill 副本创建 < 2 秒 |
| 任务列表 | 1000 条任务加载 < 1 秒 |

### 4.3 兼容性

| 项 | 要求 |
|----|------|
| 现有数据 | 新增表不影响现有数据；现有 employee 工作空间需可选迁移 |
| API | 新增字段不破坏已有接口消费方 |
| Keycloak | 支持 Keycloak 20+ |

## 十一、附录

### A. Keycloak 配置清单

需要在 Keycloak 中完成以下配置：

1. 创建 Realm（如 `digital-employee`）
2. 创建 Client（如 `de-platform`）
   - Client Protocol: `openid-connect`
   - Access Type: `public`（PKCE 模式）
   - Valid Redirect URIs: `http://localhost:3000/*`, `https://your-domain/*`
   - Web Origins: `+`
3. 创建 Realm Roles: `admin`, `manager`, `user`
4. 分配默认角色: `user`（所有新用户默认）

### B. 现有 Chat API 请求/响应格式

**当前请求**:
```json
POST /api/employees/:id/chat
{ "message": "帮我分析一下数据" }
```

**改造后请求**:
```json
POST /api/employees/:id/chat
{
  "message": "帮我分析一下附件中的数据",
  "attachments": [
    { "filename": "data.xlsx", "path": "uploads/data.xlsx" }
  ]
}
```
