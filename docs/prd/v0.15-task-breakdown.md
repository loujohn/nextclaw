# v0.15 — 平台主链路稳态化：详细任务清单

**日期**: 2026-03-31
**基于**: [升级版路线图](digital-employee-v0.15-v0.18-roadmap-v2.md)
**估算单位**: S(< 2h) / M(2-4h) / L(4-8h) / XL(1-2d)

---

## 总览

v0.15 共 8 个核心目标，拆解为 **8 个阶段**，建议按顺序执行（有前后依赖）。

| 阶段 | 名称 | 估算 | 依赖 |
|------|------|------|------|
| S1 | DB Migration 机制建立 | M | 无 |
| S2 | Schema 枚举收敛与约束补强 | L+ | S1（因 SQLite 重建表复杂度上调） |
| S3 | 统一错误分类体系 | M | 无 |
| S4 | 员工生命周期服务化 | XL | S2, S3（因 soft delete 影响范围上调） |
| S5 | 自动化调度收敛到 Job-Centric | XL | S2, S4 |
| S6 | Secrets/Integrations 进入主流程 | L | S3, S4 |
| S7 | Run/Event 可观测性补强 + 健康模型 | L | S2, S3 |
| S8 | 前端组件拆分 + 结构化日志 | XL | S8.1-S8.6 无依赖，S8.7 依赖 S4 |

## S2: Schema 枚举收敛与约束补强

**目标**：统一 status/type 字段为枚举，补充唯一性约束和索引。

### 任务清单

- [ ] **S2.1** 定义 TypeScript 层枚举常量
  - 位置：`server/db/schema.ts` 或新建 `server/db/enums.ts`
  - 枚举：
    - `EmployeeStatus = "active" | "inactive" | "archived"`
    - `RunStatus = "pending" | "running" | "completed" | "failed"`
    - `TriggerType = "manual" | "scheduled"`（注意：当前代码中 "chat" 是 trigger_source 而非 trigger_type）
    - `ScheduleKind = "cron" | "every" | "heartbeat"`
  - trigger_source 为自由文本字段，不做枚举约束
  - 复杂度：S

- [ ] **S2.2** 创建 migration：添加 CHECK 约束
  - 为 `employees.status`、`run_records.status`、`run_records.trigger_type`、`employee_schedule_jobs.schedule_kind` 添加 CHECK 约束
  - **注意**：SQLite 不支持 ALTER TABLE ADD CHECK，需通过重建表实现（CREATE new → INSERT SELECT → DROP old → RENAME），migration 前需验证现有数据无违规值
  - 复杂度：L（从 M 上调，因 SQLite 重建表复杂度）

- [ ] **S2.3** 创建 migration：添加唯一性约束
  - `employees.code` → partial UNIQUE（仅对非归档员工生效，兼容 soft delete 后复用 code）
    `CREATE UNIQUE INDEX idx_employees_code_active ON employees(code) WHERE status != 'archived'`
  - `employee_skills (employee_id, skill_name)` UNIQUE
  - `secrets.key` UNIQUE
  - 复杂度：M

- [ ] **S2.4** 创建 migration：添加查询索引
  - `run_records (employee_id, started_at DESC)`
  - `run_events (run_id, seq ASC)`
  - `employee_schedule_jobs (employee_id)`
  - 复杂度：S

- [ ] **S2.5** 更新 TypeScript 类型定义，使用枚举替代裸 string
  - 更新 `EmployeeRecord.status`、`RunRecord.status` 等类型定义
  - 更新所有 repository 层的类型引用
  - 复杂度：M

### 验收条件
- 插入非法 status 值时 DB 层拒绝
- TypeScript 编译无 type error
- 重复 employee.code 插入被拒绝

### 冒烟测试要点
- 通过 API 创建员工 → 使用 status="invalid" → 返回 400
- 创建两个同 code 员工 → 第二个返回 409
- `pnpm tsc` 无错误

- [ ] **S3.3** 更新 Run 相关 API 返回格式

- [ ] **S3.4** 更新 `shared/ui-models.ts` 中的错误显示逻辑

## S4: 员工生命周期服务化

**目标**：将员工创建/更新/删除的编排逻辑从路由层抽离到 service 层，添加事务保护。

### 任务清单

- [ ] **S4.1** 创建 `EmployeeLifecycleService`
  - 位置：`server/services/employee-lifecycle-service.ts`
  - 注入：EmployeeRepository, EmployeeSkillRepository, AutomationService, NextclawEngineGateway
  - 复杂度：M

- [ ] **S4.2** 实现 `createEmployee` 方法（含补偿式事务）
  - 步骤顺序：DB create → workspace init → skill bind → schedule create
  - 每步成功后记录"已完成步骤"
  - 任何步骤失败时按逆序回滚已完成步骤
  - 回滚逻辑：schedule → skill unbind → workspace remove → DB delete
  - 复杂度：L

- [ ] **S4.3** 实现 `updateEmployee` 方法
  - 支持 partial update
  - workspace 文件同步更新（SOUL.md, IDENTITY.md）
  - 复杂度：M

- [ ] **S4.4** 实现 `deleteEmployee` 方法（含关联清理）
  - 统一清理顺序：schedule/job 停止 → DB soft delete（status → archived）
  - workspace 策略：**不移动/不删除**，归档状态仅由 DB status 控制；workspace 在原位保留，归档后新建同 code 员工时会覆盖初始化
  - 保留 run records 和 employee_skills（归档员工恢复时可用）
  - **重要**：soft delete 影响范围广——需同步更新所有 employee 查询方法：
    - `EmployeeRepository.list()` 默认添加 `WHERE status != 'archived'`
    - `EmployeeRepository.getById()` / `getByCode()` 同理
    - 新增 `includeArchived` 参数用于管理场景
    - code 唯一性检查需考虑归档员工（归档员工的 code 不应阻塞新建）
  - 复杂度：L（从 M 上调，因查询层面改动范围较大）

- [ ] **S4.5** 重构 `index.post.ts` 调用 EmployeeLifecycleService
  - 路由层只做：readBody → 参数验证 → 调用 service → 返回结果
  - 标准：路由层不含任何业务编排逻辑
  - 复杂度：S

- [ ] **S4.6** 重构 `[id].delete.ts` 调用 EmployeeLifecycleService
  - 复杂度：S

- [ ] **S4.7** 重构 `[id].patch.ts` 调用 EmployeeLifecycleService
  - 复杂度：S

### 验收条件
- 创建员工：workspace init 失败时 DB 中无残留记录
- 创建员工：skill bind 失败时 workspace 已清理
- 删除员工：soft delete 后无残留 schedule/job，且 list API 默认不返回归档员工
- 路由层不含业务编排逻辑

### 冒烟测试要点
- 创建员工 → 验证 DB + workspace + skills 一致
- 故意制造 workspace 失败 → 验证 DB 无残留
- 删除员工 → 验证 list 不返回、jobs 已停止
- 归档员工 code 不阻塞新建同 code 员工

## S5: 自动化调度收敛到 Job-Centric

**目标**：统一到 `ejob:{jobId}` 模型，legacy schedule 标记 deprecated。

### 任务清单

- [ ] **S5.1** Legacy schedule 数据迁移工具
  - 创建 migration：将 `employee_schedules` 中的数据转换为 `employee_schedule_jobs` 记录
  - 保持业务语义不变（cron expr、heartbeat interval 等）
  - **同时处理 CronService jobs.json 持久化文件**：将 `employee:` 前缀的条目转换为 `ejob:` 格式
  - 迁移前自动备份 jobs.json 和相关 DB 数据
  - 复杂度：L

- [ ] **S5.2** 对话创建的定时任务纳入 job 模型
  - `onJob` 回调中处理 `agentId` 路径时，自动创建对应 job 记录
  - 后续执行走统一的 `ejob:` 路径
  - 复杂度：M

- [ ] **S5.3** Legacy API 标记 @deprecated
  - `upsertSchedule`、`runNow(employeeId)`、`clearSchedule` 方法加 @deprecated JSDoc
  - 内部实现改为转发到对应的 job API
  - 复杂度：M

- [ ] **S5.4** HeartbeatService 收敛到 AutomationService
  - 移除 `NextclawEngineGateway` 中的 `startHeartbeat`、`stopHeartbeat`、`stopAllHeartbeats` 方法及 `heartbeats` Map
  - 所有 heartbeat 管理统一通过 AutomationService
  - 复杂度：M

- [ ] **S5.5** `onJob` 回调简化
  - 移除三路径分发逻辑
  - 统一为：从 job name 中提取 jobId → 查 job → 查 employee → 执行

- 新建的调度任务全部走 `ejob:` 路径
- Legacy schedule 数据成功迁移为 job 记录（DB + jobs.json）
- `AutomationService.onJob` 中不再有三路径分发

### 冒烟测试要点

## S7: Run/Event 可观测性补强 + 健康模型

**目标**：统一 run 语义，修复 event seq，落地健康模型后端。

### 任务清单

- [ ] **S7.1** Run status 流转语义文档化
  - 在代码注释中明确：pending → running → completed/failed
  - 确保所有 status 赋值使用 S2 定义的枚举
  - 复杂度：S

- [ ] **S7.2** Event type 分类规范
  - 定义标准 event_type 枚举：`tool_call`, `tool_result`, `reasoning`, `message`, `error`, `heartbeat`
  - 更新 `appendEvents` 使用标准类型
  - 复杂度：M

- [ ] **S7.3**【可选】event seq 策略优化
  - 经审查：当前 appendEvents 在单次 run 内串行执行，实际并发风险极低
  - 若决定优化：改为 DB auto-increment 以降低未来扩展风险
  - 若决定不做：在代码中添加注释说明当前策略的前提假设
  - 复杂度：S（仅加注释）或 M（改 auto-increment）

- [ ] **S7.4** 创建 `EmployeeHealthService`
  - 位置：`server/services/employee-health-service.ts`
  - 两层健康模型：
    - **healthStatus**（枚举）：`unconfigured | healthy | warning | error | inactive`
    - **healthDetail**（结构体）：`{ reason, lastRunAt, consecutiveFailures, missingIntegrations }`
  - 计算逻辑：
    - 无 skills → unconfigured (reason: "no_skills")
    - status = inactive → inactive (reason: "disabled")
    - 最近 run 连续失败 → error (reason: "consecutive_failures")
    - 集成异常 → warning (reason: "integration_failed")
    - 长时间未执行 → warning (reason: "idle_too_long")
    - 最近执行成功 → healthy (reason: "recent_success")
    - 其他 → healthy (reason: "ok")
  - 复杂度：L

- [ ] **S7.5** 更新 GET /api/employees 返回标准化 health
  - 调用 EmployeeHealthService 计算每个员工的健康状态
  - 返回 `healthStatus`（枚举）+ `healthDetail`（子状态详情）两个字段
  - 保持原有 `health` 字段向后兼容（不移除 hasSkills/hasSchedule/lastStatus）
  - **性能策略**：批量计算而非逐个查询——一次性加载所有 skills/最近 runs/integrations，在内存中计算健康状态，避免 N+1 查询
  - 复杂度：M

- [ ] **S7.6** 更新 `shared/ui-models.ts` 健康类型定义
  - 新增 `EmployeeHealthStatus` type
  - 新增 `EmployeeHealthDetail` type
  - 新增 `healthStatusLabel` / `healthStatusTone` 映射函数（基于 healthStatus + detail.reason 做差异化）
  - 复杂度：S

### 验收条件
- 所有 run status 使用枚举常量
- GET /api/employees 返回 healthStatus + healthDetail 两个字段
- 无 skills 的员工 healthStatus = unconfigured, detail.reason = "no_skills"
- 原有 health 字段保持不变（向后兼容）

### 冒烟测试要点
- 新建员工（无 skills）→ healthStatus = unconfigured
- 绑定 skills + 成功执行一次 → healthStatus = healthy
- 连续 3 次执行失败 → healthStatus = error

## 建议执行顺序

```
Week 1:  S1(Migration) + S3(Error) + S8.1-S8.6(前端拆分)  [三者完全可并行]
Week 2:  S2(Schema) + S4(Lifecycle)                         [S2→S4 顺序，但可与 S8 前端并行]
Week 3:  S5(Automation) + S6(Secrets) + S7(Run+Health)      [S5 顺序，S6+S7 可并行]
Week 4:  S8.7(日志) → 集成测试 → 冒烟验证
```

## 风险与注意事项

1. **S1 baseline migration** 必须在已有数据库上验证，确保不丢数据
2. **S2 CHECK 约束** 需先确认现有数据中无违规值，否则 migration 会失败；SQLite 需通过重建表实现（见 S2.2 备注）
3. **S4 soft delete 影响广**：所有 employee 查询方法需更新，code 唯一性逻辑需重新审视
4. **S5 legacy 迁移** 需同时处理 DB 记录和 CronService jobs.json 文件，迁移前自动备份
5. **S6 secret 预检范围有限**：v0.15 仅检查模型配置和 integration 连接，skill 级别的 secret 依赖留给 v0.16
6. **S8 组件拆分** 需要逐文件验证 UI 行为不变，建议每拆一个组件验证一次
7. **API 向后兼容**：新增字段不破坏已有消费方，行为变更需明确标注
